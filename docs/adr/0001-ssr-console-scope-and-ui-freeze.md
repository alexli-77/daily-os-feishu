# ADR 0001：SSR 控制台的定位与 UI 冻结线

- 状态：已接受
- 日期：2026-09-09
- Linear：LEO-295（取代 LEO-237 的真实意图）

## 背景

原生客户端（macOS / iOS）已经有了 UI 骨架，覆盖八屏：今天 / 周期 / OKR / 对话 /
运行 / 产物 / 排程 / 设置。仓库在
[daily-os-macos](https://github.com/alexli-77/daily-os-macos) 与
[daily-os-ios](https://github.com/alexli-77/daily-os-ios)。

本仓库的服务端渲染控制台是 `src/ui/server.ts`（4965 行）+ `src/ui/pages.ts`
（2224 行），合计 7189 行 HTML-in-TypeScript。

**两者现在覆盖同一批界面。** 2026-09-07 到 09-09 三天内合入的三个控制台改进
（LEO-290 头像下拉菜单与字号三档、LEO-250 Sources 配置区整理、LEO-287
provider/模型/skill 引导），在原生骨架里全部又实现了一遍。

没有一条明确的线，往后每一屏都要付两次。

## 决定

### 一、定位：**方案 A —— headless / Docker / 远程访问的后备界面**

功能保持完整，**停止 UI 打磨**。

不选 B（砍到只剩登录 + 状态 + 诊断）的理由是具体的，不是保守：

**原生客户端今天还无法分发。** LEO-296（签名 / 公证 / 分发）尚未启动，也还没有
Apple Developer 账号。也就是说除了从源码构建，没人能装上原生客户端——
SSR 控制台是当下**唯一**可用的界面。此刻砍掉它的功能等于谁都没有界面可用。

另外，砍功能本身是工作量，而且会打破 `docs/deploy-docker.md` 与
`docs/first-customer-acceptance.md` 依赖的路径。冻结是零成本的，删除不是。

不选 C（维持双一等公民）的理由：那正是现在正在付的成本。

`Dockerfile`、`docker-compose.yml` 与上述两份文档都还在，非 Mac 用户、headless
部署、远程访问都没有别的入口。**这条线是冻结，不是弃用。**

### 二、冻结线分两个阶段生效

分阶段是为了让这条线**今天就能用**，而不是一条要等条件成熟才成立的原则。

**阶段 1 —— 现在起，直到原生客户端能装到需要它的机器上**

- 冻结**纯打磨**类改动
- 新功能**仍然进 SSR**，因为暂时没有别的选择

**阶段 2 —— 原生客户端可分发之后**

- 新功能**先进原生**
- SSR 只补「headless / Docker 用户没有其他入口」的最小可用版，且不做样式打磨

### 三、判据

| 改动类型 | 进 SSR？ |
| --- | --- |
| 安全修复 | 进 |
| 正确性 / 数据完整性 bug | 进 |
| 已有功能点了没反应之类的修复 | 进 |
| 服务端 API 变更导致的必要适配 | 进 |
| 可访问性缺陷 | 进 —— 对某些用户这是正确性，不是打磨 |
| 文案错误 / 误导性提示 | 进 |
| 纯视觉：配色、间距、排版 | 不进 |
| 交互打磨：下拉菜单、动效、字号控件 | 不进 |
| 信息架构重排 | 不进 |
| 新功能的 UI | 阶段 1 进；阶段 2 先原生 |

**拿不准时问这一句：**

> 如果这个改动不做，headless / Docker 用户还能不能完成他要做的事？

- 不能 → 进
- 能，只是更难看或更难用 → 不进

### 四、这条线不管什么

只约束 `src/ui/`。服务端、API、workflow、数据层、连接器完全不受影响——
原生客户端也要靠它们，那些投入不会付两次。

## 拿触发证据验一遍

判据要能拿具体 PR 套出是/否，否则就是口号。用引出本 ADR 的那三个 issue 检验：

| Issue | 归类 | 结论 |
| --- | --- | --- |
| LEO-290 头像下拉菜单 + 字号三档 | 交互打磨 | **不进** |
| LEO-250 Sources 配置区 UI 整理 | 纯观感 | **不进**（同 issue 里「评估 Linear MCP 用于 agent 写操作」是服务端能力，不受本线约束） |
| LEO-287 provider / 模型 / skill 引导 | 新功能 | 阶段 1 **进**；阶段 2 仍然进，因为 headless 用户装 skill 没有第二个入口，属于「必需」 |

三条得出三种不同结论，说明判据确实在区分，而不是一律否决。

## 后果

**接受的代价：** SSR 控制台会逐渐比原生端难看。这是明知的选择——它的使用者是
headless 与远程场景，那些场景里「能用」远比「好看」重要。

**换来的：** 每一屏只付一次。

**风险：** 有人（包括未来的我和 AI 协作者）会在不知情的情况下继续打磨 SSR。
缓解办法是 `AGENTS.md` 指向本文件，开工前会读到。

## 复审时机

**原生客户端第一次成功装到第二台机器上时**，回来重新评估定位——那时 B（砍到只剩
登录 + 状态 + 诊断）才第一次成为一个负责任的选项。

在那之前不要重开这个讨论。
